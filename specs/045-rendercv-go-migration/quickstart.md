# Quickstart: rendercv-go migration validation

**Feature**: 045-rendercv-go-migration
**Branch**: `045-rendercv-go-migration`

Runnable validation scenarios that prove the feature works end-to-end. These are validation/run guides — implementation details live in `tasks.md` (generated by `/speckit-tasks`).

## Prerequisites

- Go 1.26+ (the API module's version)
- `poppler-utils` installed (`pdftotext` on PATH) — used by the comparison test and the existing resume-import path; already a dev/CI dependency
- No `rendercv`, no Python, no Typst binary on PATH — the whole point of FR-011 is that none are needed
- Docker (for the image-build validation scenario)
- `pnpm` + `packages/shared` built (`pnpm install && pnpm --filter @job-finder/shared build`) — required by `make test-lint` per the constitution

## Scenario 1 — the live render test runs on a clean checkout (FR-011)

**Proves**: a resume renders with no external renderer installed; the new engine is a normal Go dependency.

```sh
cd apps/api
go test -tags live ./internal/generation/infrastructure/ -run TestLive_RenderCvRenderer_ProducesRealPDF -v
```

**Expected**: PASS. The test loads `testdata/sample_rendercv.yaml`, renders it through `RenderCvRenderer.Render` to a temp dir, and asserts the PDF exists and is non-empty. No `rendercv` binary is invoked.

**Before the migration** this test required `rendercv` on PATH; after, it requires nothing extra.

## Scenario 2 — the comparison test confirms parity (FR-013, SC-001, SC-002)

**Proves**: every document in the corpus that rendered before still renders, with matching text and page count.

```sh
cd apps/api
go test ./internal/generation/infrastructure/ -run TestRenderCvCompare -v
```

**Expected**: PASS. The test renders `testdata/sample_rendercv.yaml` and each `evaldata/cases/*/master.yaml` through the new engine, extracts text via `pdftotext` and page count via `CountPages`, and compares against the committed goldens in `testdata/compare/golden/`.

If a mismatch is found, the test fails and the difference is recorded in `testdata/compare/findings.md` with an accept-or-fix decision (FR-013). A page-count change on any corpus document is a finding, not a silent pass.

## Scenario 3 — invalid documents fail with a usable explanation (FR-005, Story 2)

**Proves**: a malformed document surfaces a field-level validation error, distinguishable from an internal failure.

```sh
cd apps/api
go test ./internal/generation/infrastructure/ -run TestRenderCvInvalidDocument -v
```

**Expected**: PASS. The test submits a document with a known defect (e.g. `cv.name: 5` — wrong type) and asserts the error message contains `"rendercv: invalid document:"` and names the offending field (`[cv name]`). A separate case asserts an internal-error path produces `"rendercv: internal error:"`.

## Scenario 4 — the page-count path works (FR-007, Story 1 scenario 3)

## Scenario 5 — the smoke render guards profiles (FR-008, Story 3)

## Scenario 6 — cancellation aborts the render (FR-006, Edge Cases)

**Proves**: a cancelled context aborts the render and produces no partial PDF.

```sh
cd apps/api
go test ./internal/generation/infrastructure/ -run TestRenderCvCancellation -v
```

**Expected**: PASS. The test creates a context, cancels it immediately, calls `Render`, and asserts the error is `context.Canceled` (wrapped) and no file exists at the expected `pdfPath`.

## Scenario 7 — the obsolete `RENDERCV_BIN` setting is tolerated (FR-010, Story 4 scenario 3)

**Proves**: the service starts when the obsolete setting is still in the environment.

```sh
cd apps/api
RENDERCV_BIN=/usr/local/bin/rendercv go test ./internal/config/ -run TestRendercvBinObsolete -v
```

**Expected**: PASS. The config loads `RENDERCV_BIN` into the struct without error; the value is never read by the renderer.

## Scenario 8 — the deployed image has no Python runtime (FR-009, SC-004, Story 4)

**Proves**: the image contains no Python, no venv, no Typst binary, and rendering works inside it.

```sh
make images
docker run --rm job-finder-api:local-check sh -c 'which python3 python pip typst; test $? -ne 0 && echo "no python/typst found"'
docker run --rm job-finder-api:local-check sh -c 'ls /opt/rendercv-venv 2>/dev/null && echo "venv present" || echo "no venv"'
```

**Expected**: `no python/typst found` and `no venv`. Then render inside the container:

```sh
docker run --rm -v "$PWD/data/documents:/data/documents" job-finder-api:local-check \
  sh -c 'echo "cv:\n  name: Test\n  sections:\n    experience:\n      - company: Acme\n        position: Engineer" > /tmp/cv.yaml && ...'
```

(A container-level render is best validated via the API's `/api/health/ready` + a generation request in a `docker compose` stack, since the renderer is an internal library, not a CLI inside the container.)
