# Research: Resume Generation Strictness & Model Improvement

**Feature**: 033-resume-gen-strictness
**Date**: 2026-08-07

## R1. The strictness gap at the default grounding level

**Decision**: Extend `VerifyRendercvGrounding` to enforce skill-token grounding at the
**moderate** and **aggressive** levels (not only `strict`), and run
`DropUngroundedSkillTokens` after the primary tailoring merge — not only after the
expand/condense page-fitting passes.

**Rationale**: The code audit (`apps/api/internal/generation/domain/rendercv_grounding.go:95-163`)
shows the skill-token check is gated behind `if level == GroundingStrict` (line 133). The
default grounding level is `moderate` (`apps/api/internal/config/defaults.go:18`), so the
overwhelming majority of runs have **no skill-token enforcement** on the primary pass.
`DropUngroundedSkillTokens` (`rendercv.go:178-194`) exists and silently drops ungrounded
tokens, but it is called only at `service.go:359` (after expand) and `service.go:398`
(after condense) — never after the initial `selectAndTailor` merge at `service.go:228`.

This is the root cause of "problems with AI resume generation strictness": a fabricated or
unrelated skill token passes the verifier at the default level and reaches the review surface.
Constitution II (Grounded Generation) is violated without any detection.

**Alternatives considered**:
- *Tighten the prompt only.* Rejected as the sole fix — the prompt already says "do not
  fabricate," and the model still does. The verifier is the guarantee; the prompt is the first
  line of defense, not the only one.
- *Switch the default to `strict`.* Rejected — `strict` forbids adding adjacent skills the
  vacancy asks for, which materially weakens tailoring quality. The fix is to enforce what
  `moderate` already promises (adjacent-only), not to collapse `moderate` into `strict`.

## R2. Highlight-drift detection (the unused `lcsCovered` check)

**Decision**: Wire `lcsCovered` (≥50% word overlap, `rendercv_grounding.go:59-74`) into the
production grounding loop, applied to every experience highlight in the merged resume at all
grounding levels. A highlight below the threshold is a grounding violation; after a failed
re-prompt, the offending highlight is replaced with its closest master bullet (strip-and-log,
same pattern as `StripStructureViolations`).

**Rationale**: `VerifyTailoredSectionsGrounding` (`rendercv_grounding.go:8-57`) already
implements this check against the `TailoredSections` payload, but it has **no production
caller** — the flow uses `VerifyRendercvGrounding` against the merged document instead, which
does not check highlight word-overlap at all (except strict project-highlight tokens). So a
highlight can be substantially rewritten/fabricated as long as the company name matches and no
years-assertion is triggered. This is a second hole in Constitution II.

**Alternatives considered**:
- *Call `VerifyTailoredSectionsGrounding` instead of `VerifyRendercvGrounding`.* Rejected —
  the merged-document check catches things the payload check can't (a section key the merge
  somehow added). Keep both; the merged check gains the highlight-overlap pass.
- *Drop the highlight entirely on violation.* Rejected as the first step — a dropped bullet
  leaves a gap. The strip-and-log fallback replaces it with the closest master bullet so the
  resume is never thinner than the master, matching the "never emit a partially-grounded
  resume" principle while not failing the whole run.

## R3. The stale prompt field reference

**Decision**: Remove the `sectionsToDrop` reference from `buildSelectPrompt`
(`rendercv_llm.go:173`) and audit all prompt builders for references to removed `TailoredSections`
fields (`sectionsToDrop`, `ExperienceOrder`, `Drop`).

**Rationale**: 028 removed these fields from `TailoredSections` (`rendercv.go:72-81`) to make
structural violations unrepresentable (spec §3.1). The prompt still says
`"Do not populate sectionsToDrop."` — harmless (the schema won't include the field) but a
contract drift signal: the prompt and the data contract disagree. A future reader of the prompt
would infer the field exists. This is a low-risk, high-clarity fix.

**Alternatives considered**: *Leave it as defense-in-depth.* Rejected — the schema is the
contract the model sees; a prose reference to a non-existent field is noise, not defense.

## R4. Strict JSON Schema (`json_schema` with `strict: true`) vs `json_object`

**Decision**: Upgrade the structured-output path to send
`response_format: { "type": "json_schema", "json_schema": { "name": "<type>", "schema": <schema>, "strict": true } }`
with `additionalProperties: false`, for the `generation` task's structured calls. The schema is
already generated by `CompleteStructured` (`port.go:84-97`) via `jsonschema.ReflectFromType` —
it just isn't sent to the model as a strict constraint today; it's appended to the prompt as
text and the model is trusted to follow it.

**Rationale**: LiteLLM proxy supports `json_schema` with `strict: true` across OpenAI, Groq,
Ollama, Anthropic, Gemini, Bedrock and Databricks (LiteLLM docs, "Structured Outputs (JSON
Mode)"). The current `chatRequest.ResponseFormat` (`gateway.go:55`) is
`map[string]string` — it can only express `{"type": "json_object"}`, the weak mode. Upgrading
the request type to a struct (or `any`) lets the gateway send the full `json_schema` shape.
This constrains the model at the API level: it **cannot** emit unexpected fields, and the
schema is enforced by the provider, not by prose. This directly reduces the violation rate at
the source (spec FR-005, SC-001).

**Capability trap (030-C5) handling**: The gateway config already guarantees every model in
every chain is `response_format: json_object`-capable (verified against provider catalogs at
implementation time). The same contract is extended: every model in the `generation` chain
must be `json_schema`-capable. This is verified at implementation time, not at runtime — the
app does not know which upstream model served the request (030-FR-004), so runtime capability
detection in the Go app is impossible. The `drop_params: true` setting means an unsupported
`json_schema` param would be silently dropped, degrading into prose — the capability trap.
The guard is the config-time verification, exactly as 030-C5 prescribes.

**Alternatives considered**:
- *Runtime capability detection via `get_supported_openai_params`.* Rejected — that is a
  Python LiteLLM SDK function; the Go app talks to the proxy, not the SDK. The proxy does not
  expose a "does this model support json_schema" endpoint to the client. Config-time
  verification is the established pattern (030-C5).
- *Send `json_schema` for all tasks, not just generation.* Out of scope for this feature —
  `match`, `rephrase`, `ghost`, `default` would each need their chain re-verified for
  `json_schema` support. Generation is the quality-critical task (030 config comment, lines
  50-54); the others keep `json_object` and the existing retry loop. A per-call mode selector
  in `CompleteOptions` lets a future feature upgrade them without changing the adapter again.

**Fallback for non-strict providers**: When a provider/model does not support
`json_schema` (a future chain entry not yet verified), the call must fall back to
`json_object` mode and the existing JSON-parse retry loop (`CompleteStructured`,
`port.go:104-127`). This is expressed as a per-call `ResponseMode` on `CompleteOptions`:
`ResponseModeStrict` (send `json_schema`), `ResponseModeJSON` (send `json_object`, current
behaviour). The generation call sites set `ResponseModeStrict`; everything else defaults to
`ResponseModeJSON`, preserving today's behaviour exactly.

## R5. Max output tokens

**Decision**: Set `max_completion_tokens` explicitly for generation calls, via
`CompleteOptions.MaxTokens`. Derive a sensible default from the `TailoredSections` shape: a
generous cap that never truncates a valid one-page resume payload but bounds a runaway
response. A value around 4096 tokens covers the largest expected `TailoredSections` (summary +
~10 skill groups + ~10 experience entries with 10 highlights each + projects) with headroom.

**Rationale**: Today `MaxTokens` is never set by any generation call site, so
`chatRequest.MaxCompletionTokens` (`gateway.go:54`, `omitempty`) is absent from the request.
A long tailoring response is bounded only by the model's implicit limit or the 60s
`request_timeout` per attempt. An explicit cap is a deterministic guard and lets the provider
allocate capacity. This is spec FR-012.

**Alternatives considered**: *Leave it unset.* Rejected — an unbounded response can hit the
request timeout and surface as a 5xx, which is classed as retryable and advances the chain,
costing a full tier cycle on what was really a truncation. An explicit cap fails fast with a
parseable error instead.

## R6. Model re-evaluation for the `generation` task

**Decision**: Run an empirical strictness benchmark across every model in the generation chain
before shipping, measuring (a) grounding violation rate, (b) structural violation rate,
(c) JSON-parse failure rate. The primary model is the one with the lowest combined violation
rate, not the one with the highest general-quality score. Document the results in this file's
successor (folded into the domain doc on ship).

**Current generation chain** (`gateway/config.yaml:50-70, 164`):
| Tier | Model | Provider |
|---|---|---|
| 1 (primary) | `openrouter/deepseek/deepseek-v4-pro` | OpenRouter (may be paid) |
| 2 | `cerebras/gpt-oss-120b` | Cerebras (free) |
| 3 | `groq/llama-3.3-70b-versatile` | Groq (free) |
| 4 | `cohere_chat/command-r-08-2024` | Cohere (free) |
| terminal | `ollama_chat/gpt-oss:120b-cloud` | Local Ollama |

**Rationale**: The current primary (`deepseek-v4-pro`) was chosen for "output quality" (config
comment, line 53) — a general criterion, not a strictness criterion. The spec's complaint is
about rule strictness, so the evaluation must measure rule strictness. DeepSeek V4 Pro remains
a strong candidate (strong reasoning, supports `json_schema`), but the decision is now
evidence-backed. All four hosted models + local Ollama support `json_schema` strict mode (per
LiteLLM's supported-providers list and the existing config-time verification pattern), so the
upgrade in R4 does not preclude any of them.

**Alternatives considered**:
- *Keep `deepseek-v4-pro` without evaluation.* Rejected — the user explicitly asked to
  "investigate better models." An unevaluated default is what got us here.
- *Switch to a single "best" model from external benchmarks.* Rejected — external benchmarks
  measure general capability, not obedience to *this* system's grounding rules. The benchmark
  must run the actual tailoring pipeline against the actual verifier.

**Benchmark design**: Fix a set of master profiles (varied: short, long, sparse skills, dense
skills) and vacancies (varied: skills present, skills absent, adjacent skills). For each
model × profile × vacancy, run the full `tailorRendercvResume` pipeline and record:
grounding violations (skill tokens, highlight overlap), structural violations (years
assertions), JSON-parse failures, and wall-clock time. The primary model is the lowest
combined-violation model that still meets 020-SC-007 (under 60s average on local model).
