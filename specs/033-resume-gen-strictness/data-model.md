# Data Model: Resume Generation Strictness & Model Improvement

**Feature**: 033-resume-gen-strictness
**Date**: 2026-08-07

This feature introduces **no new persisted entities** and **no schema migrations**. Every
change is to in-memory validation, prompt construction, and request shaping. This document
records the existing entities the feature extends and the new in-memory types, so the
implementation phase has a single reference.

---

## Existing entities (extended, not changed)

### GroundingLevel

**File**: `apps/api/internal/generation/domain/rendercv.go:13-28`

```
type GroundingLevel string
const (
    GroundingStrict     = "strict"
    GroundingModerate   = "moderate"   // the default
    GroundingAggressive = "aggressive"
)
```

No change to the type or constants. The change is to what each level *enforces*:
`VerifyRendercvGrounding` currently checks skill tokens only under `GroundingStrict`; after
this feature it checks them at all levels (with the adjacency allowance for
moderate/aggressive expressed as "token must be in master OR be a recognized adjacent token"
— see `AdjacentSkillAllowed` below).

### GroundingViolation (in-memory)

**File**: `apps/api/internal/generation/domain/rendercv_grounding.go` — return type of
`VerifyRendercvGrounding` is `[]string`.

Today: strings like `skill "X" (label) not in master profile (strict grounding)`.
After: the same function returns strings for skill-token violations at all levels, plus new
highlight-drift strings: `experience "Acme" highlight not grounded in master: "<truncated>"`.

No struct change — the violation is still a string. The set of strings it can return grows.

## New in-memory types

### ResponseMode

**File**: `apps/api/internal/platform/llm/domain/port.go` (add to `CompleteOptions`)

```
type ResponseMode int
const (
    ResponseModeJSON   ResponseMode = iota  // current behaviour: json_object
    ResponseModeStrict                       // json_schema with strict: true
)

type CompleteOptions struct {
    System      string
    Temperature *float64
    MaxTokens   *int
    Model       string
    ResponseMode ResponseMode   // NEW — defaults to ResponseModeJSON (zero value)
}
```

The zero value (`ResponseModeJSON`) preserves today's behaviour for every caller that does not
opt in. The generation call sites set `ResponseMode: ResponseModeStrict`.

**Why an enum, not a bool**: a future feature may add `ResponseModeText` (no JSON enforcement)
or `ResponseModeSchema` (send schema but not strict). An enum is forward-compatible; a bool
is not.

### StrictSchemaRequest

**File**: `apps/api/internal/platform/llm/infrastructure/gateway/gateway.go`
(replace `chatRequest.ResponseFormat map[string]string`)

```
type responseFormat struct {
    Type       string         `json:"type"`                 // "json_object" | "json_schema"
    JSONSchema *jsonSchema   `json:"json_schema,omitempty"` // present only for json_schema
}
type jsonSchema struct {
    Name   string         `json:"name"`
    Schema map[string]any `json:"schema"`
    Strict bool           `json:"strict"`
}

type chatRequest struct {
    Model               string                 `json:"model"`
    Stream              bool                   `json:"stream"`
    Messages            []chatMessage          `json:"messages"`
    Temperature         float64                `json:"temperature"`
    MaxCompletionTokens *int                   `json:"max_completion_tokens,omitempty"`
    ResponseFormat      *responseFormat        `json:"response_format,omitempty"`   // pointer: omit when nil
}
```

`CompleteJSON` builds `ResponseFormat` from `opts.ResponseMode`:
- `ResponseModeJSON` → `&responseFormat{Type: "json_object"}`
- `ResponseModeStrict` → `&responseFormat{Type: "json_schema", JSONSchema: &jsonSchema{Name, Schema, Strict: true}}`

The schema itself is generated by `CompleteStructured` (`port.go:84-97`) via
`jsonschema.ReflectFromType` and passed to the provider through a new `CompleteOptions` field
or a separate `CompleteStructuredOpts`. The cleanest path: `CompleteStructured` sets
`opts.ResponseMode = ResponseModeStrict` and passes the schema string; the gateway adapter
parses it into `map[string]any` and builds the `jsonSchema`. The schema is cached in
`schemaCache` (`port.go:82`) so the parse happens once per type.

### AdjacentSkillAllowed (optional, under moderate/aggressive)

**File**: `apps/api/internal/generation/domain/rendercv_grounding.go` (new helper)

Under `GroundingModerate`, the prompt allows adding "directly adjacent" skills. The verifier
cannot know adjacency a priori, but it can apply a **deny-list** of obviously unrelated tokens
that the vacancy asks for but the master has no trace of. The simplest correct rule:

> Under moderate, a skill token is grounded if it is in `MasterSkillTokens(master)` OR is in
> the vacancy's `RequiredSkills`/`NiceToHaveSkills` AND at least one master skill token shares
> a coarse category (same first token, e.g. "aws"/"terraform" both cloud, or a curated
> adjacency map). In practice, the safe first cut is: allow a vacancy-required token only if the
> master already has a token in the same group label (e.g. "Cloud" group exists → allow
> Terraform). If that proves too permissive, fall back to strict-only (master tokens only) and
> document moderate as "strict + reorder".

This is the one design decision left to the implementation phase to tune against the
benchmark (R6). The data model is: `AdjacentSkillAllowed(master, token, vacancyAnalysis)
bool`. The signature is fixed; the heuristic inside it is the tuning knob.

## State transitions

### Grounding loop (`service.go:210-245`)

Current:
```
for attempt := 0; attempt < 2; attempt++ {
    payload = selectAndTailor(...)
    merged = MergeTailored(...)
    ApplyHardLimits(...)
    violations = VerifyRendercvGrounding(master, merged, level)
    if len(violations) == 0 {
        return fixStructureIntegrity(...)  // years check
    }
}
return error("failed grounding check")
```

After:
```
for attempt := 0; attempt < 2; attempt++ {
    payload = selectAndTailor(...)        // strict schema + cleaned prompt
    merged = MergeTailored(...)
    ApplyHardLimits(...)
    DropUngroundedSkillTokens(master, merged)   // NEW — run on primary pass too
    violations = VerifyRendercvGrounding(master, merged, level, analysis)  // extended
    if len(violations) == 0 {
        return fixStructureIntegrity(...)        // now also checks highlight drift
    }
    lastViolations = violations                  // feed back into re-prompt
}
return error("failed grounding check")
```

`fixStructureIntegrity` gains a second check: after `VerifyStructureIntegrity` (years), it
also calls `VerifyHighlightGrounding` (new, or folded into `VerifyRendercvGrounding`). On
violation, one re-prompt; on recurrence, `StripUngroundedHighlights` (new, mirrors
`StripStructureViolations`) replaces the drifted highlight with its closest master bullet and
logs.

### Expand/condense passes (`service.go:349-398`)

After `MergeTailored` on the expand/condense result, the same
`DropUngroundedSkillTokens` + `VerifyRendercvGrounding` + `VerifyHighlightGrounding` chain
runs. Today only `DropUngroundedSkillTokens` + `ApplyHardLimits` runs. The strictness checks
now apply uniformly (spec FR-009).

## No database changes

- No new tables, no new columns, no migrations.
- The `edit_proposals.dropped_reason` column and `EditProposal.DroppedReason` field already
  exist (migration `00032` era); this feature does not wire the proposal-dropped lifecycle
  (that remains a separate future feature). The current fallback (strip and log on the
  activity row) is the operative behavior, consistent with the years-assertion pattern.
