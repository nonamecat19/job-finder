# Implementation Plan: Company Intel Card

**Branch**: `004-company-intel-card` | **Date**: 2026-07-20 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-company-intel-card/spec.md`

## Summary

Surface company-level intelligence on the job detail page — funding, layoffs, Glassdoor rating, headcount trend, and tech stack — via scraping public pages (Crunchbase, layoffs.fyi, Glassdoor, BuiltWith, company About page). Five signal scrapers, each best-effort and independently failing. Two new DB tables (`company`, `company_signal`) behind migration 00007. One new API endpoint for manual refresh. One new dashboard card component. Refresh is manual-only per user decision.

## Technical Context

**Language/Version**: Go 1.23+ (`apps/api`) for backend scrapers + endpoint; TypeScript/React (`apps/dashboard`) for frontend card.

**Primary Dependencies**: `github.com/PuerkitoBio/goquery` (HTML parsing — already vendored), existing `internal/scraping.Service` (HTTP fetch — already vendored). Frontend uses existing component library (Tailwind CSS, likely shadcn/ui). No new external dependencies.

**Storage**: PostgreSQL via sqlc. New migration `00007_company_intel.sql` adding `company` and `company_signal` tables. sqlc regenerate required.

**Testing**: `go test ./internal/companyintel/...` for scrapers; `go test ./...` for regressions. Frontend tests via vitest with `apps/dashboard`. Live parity smoke tests behind `//go:build live` tag.

**Target Platform**: Linux server (Docker Compose), same container as the rest of `apps/api` + browser for dashboard.

**Project Type**: Full-stack feature — Go backend scrapers + HTTP handler + SQL, TypeScript/React dashboard card.

**Performance Goals**: Card renders in <2s (no backend call needed when signals exist — preloaded in the page data). Refresh completes in ~60s worst case (5 sources × 2s pacing + HTTP overhead = ~12s typical, 60s allows for timeouts and retries).

**Constraints**: External sites are unreliable. Every scraper must fail independently and gracefully. The refresh endpoint must not block other API requests.

**Scale/Scope**: Single-user self-hosted deployment. ~5 signal scrapers + 1 API handler + 1 dashboard component + 1 migration. Estimated ~500 LOC backend + ~200 LOC frontend.

### Scraping External Pages — New Constitution Surface

This feature introduces a *new category* of external scraping not present in spec 001: company intelligence signals from non-job-board sites. Each site is evaluated against the Constitution:

| Site | Target | Constitution Assessment |
|------|--------|------------------------|
| **Crunchbase** | Public company profile page (`crunchbase.com/organization/{slug}`) | ✅ PASS. Public page, no login wall, no bot challenge. Standard `GET` with a browser User-Agent. The same scraping approach as work.ua (spec 001). |
| **layoffs.fyi** | Public layoff tracker page | ✅ PASS. Public page, no login, no challenge. Minimal risk of layout changes. |
| **Glassdoor** | Public review summary page | ⚠️ **BEST-EFFORT (FAIL-CLOSED)**. Acknowledged ToS gray area per user direction. The scraper targets *public* review pages and does not bypass a login wall. If Glassdoor challenges or blocks, the signal fails closed (omitted from card, logged warning). This is accepted by the user. Constitution Principle I remains intact because the scraper only reads — no form posting, no review submission, no account-level action. |
| **BuiltWith** | Public technology lookup page | ✅ PASS. Public page, no login wall. Standard scraping. Falls back to job posting's required-skills section when unreachable (FR-015). |
| **Company About page** | Company's own website | ✅ PASS. The company's own public page. Headcount extraction is inherently fragile (no standard layout) but best-effort and non-critical. |

**No violations.** The Glassdoor case is explicitly flagged, user-accepted, and fails closed — exactly the pattern the Constitution's "best-effort external dependency" language anticipates.

## Key Design Decisions

Full reasoning in [research.md](./research.md). Summary:

1. **Scraper architecture**: Each signal source gets its own scraper function behind a shared `Scraper` interface (`scrape(ctx, company, website) (*SignalResult, error)`). A registry maps `kind → scraper`. This keeps failures isolated (FR-006) and makes adding/removing signal sources a one-file change.
2. **Refresh endpoint**: `POST /jobs/{id}/company-intel/refresh` — synchronous from the caller's perspective but internally parallelizes scrapers per domain. All scrapers for distinct domains run concurrently (each domain-paced independently). Typical 5-source refresh completes in ~12s (max pacing = 2s per domain, 5 domains × 2s worst-case sequential = 10s, but parallel across domains means the bottleneck is the *longest single scrape*).
3. **Company resolution**: `normalizedName = lower(trim(job.Company))`. Simple, exact, indexable. No fuzzy matching in V1. The lookup is an upsert: `INSERT ... ON CONFLICT (normalized_name) DO NOTHING RETURNING id` followed by a `SELECT` if no row was inserted.
4. **Pacing**: 2-second minimum interval per domain, matching the crawl-delay convention established in spec 001. Implemented with a per-domain rate limiter (`map[host]time.Time` + sleep), not a global delay. This means Crunchbase and Glassdoor can be scraped in parallel (different domains).
5. **Tech stack fallback**: Primary source is BuiltWith public lookup. When BuiltWith returns non-2xx, the scraper falls back to parsing the job posting's `description` for technology keywords (a shared list of ~100 common frameworks/languages/tools). When both fail, the signal is omitted (FR-015).
6. **Headcount baseline**: First scrape records a headcount with `trend: "baseline"`. Second scrape (manual refresh) records `current` and `previous`, computes `trend`. Until a second scrape exists, the card shows "baseline captured — refresh to see trend."
7. **No UI state on backend**: The card's loading/error states are managed entirely in the React component. The API returns the latest signals (which may be pre-cache from a previous scrape) and a `sources` array indicating per-source success/failure. The dashboard never blocks on slow scrapes — the refresh endpoint is the only write path and the user explicitly triggers it.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Glassdoor blocks us after a few scrapes | Medium (known anti-scraping posture) | Signal fails closed gracefully (FR-006); user acknowledged ToS gray area. Logged at `slog.Warn` for diagnosis. |
| Crunchbase changes page layout | Low (stable structure for years) | HTML fixture saved at Phase 0; live smoke test catches drift; zero-results path degrades to "no data" per spec. |
| Company About page has no recognizable headcount | High (no standard layout) | Scraper uses heuristic selectors (`h2:contains("Team")`, `h2:contains("About")`, etc.) with fallbacks. If no number found, headcount signal is omitted with a logged warning — never a card error. |
| BuiltWith blocks us | Low | Falls back to job posting's required-skills section (FR-015). If that is also empty, the signal is omitted. |
| Multiple jobs at the same company cause concurrent Company row creation | Low | `ON CONFLICT (normalized_name) DO NOTHING` makes the insert idempotent. Race-safe by design. |
| Refresh endpoint is slow (~12s) and user navigates away | Medium | The endpoint is stateless — in-flight scrapes are abandoned when the request context is cancelled. No partial DB writes from cancelled requests (each successful scrape writes atomically; a cancelled request leaves previously-completed signals in place). |
