# Feature Specification: User-Selectable Resume Generation Model

**Feature Branch**: `034-resume-model-choice`

**Created**: 2026-08-07

**Status**: Draft — **not planned, not built. Rescope before planning.**

**Input**: User description: "current ai model for resume generation is not good as needed. the model should be more strict. investigate different models by quality/price from openrouter and add ability for user to pick one of 3-5 models for resume"

## Standing note (added 2026-08-08)

This spec has no `plan.md`, `research.md` or `tasks.md`, and no code answers to it — the grep for a
model selector across `apps/dashboard`, `packages/shared` and `internal/generation` returns nothing.
That is deliberate, but the reason was recorded only in the commit message that created this file
(`d064c91`), where nobody looking at the feature directory would find it. Restating it here.

**Two of this spec's three user stories have been overtaken.**

- **US2 (curated options measured, not guessed)** is now 038's job. The scored golden-set harness
  runs the six deterministic corpus cases against candidate models and writes a per-model,
  per-case, per-stage artifact with cost, latency and served model. That is the measurement US2
  asks for, and it exists —`go test -tags eval_live ./internal/generation/application/ -run
  TestLiveComparison -eval.models <a>,<b>`. What US2 still lacks is one live invocation and a
  decision about which 3-5 options to publish.
- **US1 (the picker itself)** needs rescoping, not implementing as written. 035 split generation
  into five stages served by different models. Offering the user a choice over *the* generation
  model no longer maps onto anything: the mechanical stages (analyze, select) are not worth
  exposing — the economy model does them as well as the premium one — and the choice that carries
  real quality and cost is the **summary stage**. A picker over five stages is a settings panel
  nobody wants; a picker over the summary is the feature the user actually asked for.
- **US3** should be re-read against 035's per-stage cost recording before it is planned.

**Before anyone runs `/speckit-plan` on this**: scope US1 down to a summary-stage choice, and cut
or rewrite the FRs that assume a single generation model. Planning it as written would produce
tasks against a pipeline shape that no longer exists.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Pick the model that writes my resume (Priority: P1)

A user about to tailor a resume for a job sees a short, named list of generation quality
options — 3 to 5 of them — each labelled with what it is good at and roughly what it costs
per resume, plus the always-available self-hosted option. They pick one, run the tailoring,
and the resume is produced by the option they chose. The choice is visible on the result, so
they know which option produced which resume.

**Why this priority**: This is the whole ask. Today the model serving resume generation is
fixed by an operator-edited config file; a user who finds the output too loose, too generic,
or too slow has no lever at all. Giving them a small, curated, labelled choice is the
minimum viable slice and delivers value on its own even if nothing else in this feature ships.

**Independent Test**: Can be fully tested by opening the tailoring surface, selecting each
offered option in turn, running a tailoring pass for each, and asserting the run completes and
records the selected option — no other part of this feature needed.

**Acceptance Scenarios**:

1. **Given** the tailoring surface is open, **When** the user views the generation options,
   **Then** between 3 and 5 named options are listed, each with a short quality description and
   a relative cost indicator, plus the self-hosted option, and exactly one is preselected as
   the default.
2. **Given** the user selects a non-default option, **When** they run tailoring, **Then** the
   resume is generated by that option and the completed run displays which option produced it.
3. **Given** the user does not touch the selector, **When** they run tailoring, **Then** the
   default option is used and the behaviour is identical to today's for a user who never
   discovers the feature.
4. **Given** a user has selected an option, **When** they return to the tailoring surface
   later, **Then** their last choice is remembered as their default rather than reverting.

---

### User Story 2 - Curated options chosen for strictness, not just for being expensive (Priority: P2)

The options offered are not an arbitrary model dump. Each one has been measured against the
rules resume generation actually has to obey — stay grounded in the master profile, emit
well-formed structured output, respect the section and length constraints — and the list spans
a deliberate quality/cost range so a user can trade money for strictness knowingly. The
default is the option with the best measured rule-compliance at a cost the operator considers
routine.

**Why this priority**: A picker over unmeasured options just moves the guesswork to the user.
The measurement is what makes the choice meaningful, and it is what answers the user's actual
complaint ("the model is not strict enough"). It is P2 rather than P1 because the picker is
still useful with a hand-reasoned list, and the evaluation can land right behind it.

**Independent Test**: Can be tested by running the shared benchmark fixture through every
offered option and asserting each has a recorded rule-violation rate, that the offered set
spans at least a 5x cost range end to end, and that the default is the option with the lowest
violation rate within the operator's routine-cost band.

**Acceptance Scenarios**:

1. **Given** the candidate options, **When** each is run against the same benchmark master
   profile and vacancy set, **Then** each records a grounding-violation rate, a structural
   violation rate, a malformed-output rate, and a median run duration.
2. **Given** those measurements, **When** the offered list is assembled, **Then** every offered
   option supports strict structured output, and any candidate that cannot be constrained by an
   output schema is excluded from the list regardless of its general reputation.
3. **Given** the offered list, **When** a user compares the cheapest and most expensive option,
   **Then** the difference in cost per resume and in measured strictness is stated in terms
   they can act on, not as raw model identifiers.

---

### User Story 3 - Falling back without silently changing the answer (Priority: P2)

A user picks a premium option, but that provider is rate-limited, out of credit, or down. The
run still completes — the system falls back down the chain and ultimately to the self-hosted
model — and the user is told plainly that their chosen option was unavailable and which one
actually produced the resume. They can retry or accept.

**Why this priority**: A picker creates an expectation the current failover silently breaks. A
user who chose the strictest option and unknowingly received the loosest one is worse off than
before the feature existed — this directly threatens the trust the product is built on.

**Independent Test**: Can be tested by making the selected option's provider unavailable,
running a tailoring pass, and asserting the run completes, the resume is produced by a
fallback, and the surface states which option was actually used and that it was not the one
chosen.

**Acceptance Scenarios**:

1. **Given** the user's chosen option is unavailable (no credential, rate-limited, out of
   credit, or unreachable), **When** they run tailoring, **Then** the run completes via the
   fallback chain, which terminates at the self-hosted model, and never fails purely because
   the chosen option was unavailable.
2. **Given** a run served by a fallback rather than the chosen option, **When** the user views
   the result, **Then** it is labelled with the option that actually served it and marked as a
   substitution.
3. **Given** every hosted option is unavailable, **When** the user runs tailoring, **Then** the
   self-hosted option produces the resume and the system remains fully functional.

---

### User Story 4 - The operator still owns which models exist (Priority: P3)

The operator curates the offered list — adding, removing, repricing, or repointing an option —
by editing the deployment's routing configuration and restarting that one service. No
application rebuild, no database migration, no code change, and no provider credential ever
becomes visible to the application or the user.

**Why this priority**: It preserves the existing operational contract and the project's
self-hosting guarantees. It is P3 because it protects an invariant rather than delivering new
user-visible value, but a picker that hardcodes model identities into the application would
violate constraints the platform depends on.

**Independent Test**: Can be tested by changing which underlying model backs one offered
option, restarting only the routing service, and asserting the user-facing option label is
unchanged while the served model differs — with no rebuild or migration performed.

**Acceptance Scenarios**:

1. **Given** the operator repoints an offered option at a different underlying model, **When**
   the routing service is restarted, **Then** users see the same option name and the new model
   serves it, with no application deployment.
2. **Given** the operator removes an option that some users had selected, **When** those users
   next run tailoring, **Then** the run succeeds using the default option and the user is told
   their previous choice is no longer available.
3. **Given** any offered option, **When** its configuration is inspected, **Then** its fallback
   chain terminates at the self-hosted model and no provider credential is readable through the
   application or the dashboard.

---

### Edge Cases

- What happens when the user's stored choice names an option the operator has since removed or
  renamed? The run must not fail: it falls back to the default and tells the user their choice
  is gone.
- What happens when the offered list is empty or misconfigured (fewer than the minimum
  options)? The tailoring surface must still work with the self-hosted option alone.
- What happens when a chosen premium option is far slower than the default? The user is warned
  before the run if an option is known to be slow, and the existing run timeout still applies —
  a slow option must not hang the queue indefinitely.
- What happens when a queued background generation runs long after the user's selection
  changed? The run uses the choice captured at enqueue time, not the choice at execution time,
  so the label on the result is always truthful.
- What happens to cost when a user repeatedly re-runs on the most expensive option? Per-run
  cost is shown before the run; the feature does not add spend controls, which is called out as
  out of scope.
- What happens when a chosen option produces output the grounding rules reject twice in a row?
  The existing strictness behaviour applies unchanged (feature 033) — the model choice does not
  weaken any grounding rule.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Users MUST be able to choose the generation option used for a resume tailoring
  run from a curated list of between 3 and 5 hosted options plus the always-available
  self-hosted option.
- **FR-002**: Each offered option MUST be presented with a human-meaningful name, a one-line
  description of what it is best at, an indicative cost per resume, and an indicative speed —
  never as a raw provider or model identifier.
- **FR-003**: The system MUST apply a default option when the user makes no explicit choice,
  and that default MUST reproduce today's behaviour for users who never interact with the
  selector.
- **FR-004**: A user's most recent choice MUST persist as their personal default across
  sessions, and MUST be changeable at any time.
- **FR-005**: The chosen option MUST be captured at the moment the run is requested and applied
  to that run, so a later change of preference cannot alter an in-flight run.
- **FR-006**: A completed run MUST record and display which option actually produced the
  resume, and MUST mark the run when that differs from the option the user chose.
- **FR-007**: When the chosen option is unavailable, the run MUST continue down its fallback
  chain rather than failing, and every chain MUST terminate at the self-hosted model.
- **FR-008**: The application MUST request generation by option name only; provider identities,
  model identifiers, and provider credentials MUST NOT be sent by, stored in, or readable
  through the application or the dashboard.
- **FR-009**: Every offered hosted option MUST support strict schema-constrained structured
  output; a candidate that cannot be constrained by an output schema MUST NOT be offered.
- **FR-010**: The offered options MUST each be evaluated against the shared strictness
  benchmark before being offered — recording grounding-violation rate, structural violation
  rate, malformed-output rate, median duration, and measured cost per resume — and the results
  MUST be documented alongside the option list.
- **FR-011**: The offered set MUST span a deliberate quality/cost range, with the most
  expensive offered option costing at least 5x the cheapest hosted one per resume, so the
  choice is a real trade-off rather than cosmetic.
- **FR-012**: The default option MUST be the option with the lowest measured combined violation
  rate among those within the operator's routine-cost band, and the rationale MUST be recorded.
- **FR-013**: Adding, removing, repricing, or repointing an option MUST be an operator
  configuration change plus a restart of the routing service only — no application rebuild, no
  schema migration, no code change.
- **FR-014**: If a user's stored choice is no longer offered, the system MUST fall back to the
  default option, complete the run, and inform the user their choice is unavailable.
- **FR-015**: Selecting any option MUST NOT weaken, bypass, or reconfigure any grounding or
  structural rule; all generated content remains subject to the same verification regardless of
  which option produced it.
- **FR-016**: Every run MUST record its chosen option, its serving option, and its outcome on
  the run's activity record, so an operator can audit which options are actually being used and
  how often substitution occurs.
- **FR-017**: The selector MUST be available on both the ad-hoc tailoring surface and any
  job-triggered resume generation entry point, so the choice is not limited to one path.

### Key Entities *(include if feature involves data)*

- **Generation Option**: a user-facing, operator-curated choice of generation quality — name,
  description, indicative cost per resume, indicative speed, and availability. It is an
  abstraction over an ordered chain of models, not a single model identity.
- **User Generation Preference**: the option a given user last chose; their personal default
  for subsequent runs. Falls back to the system default when absent or no longer offered.
- **Generation Run Record**: an existing per-run record, extended with the option chosen at
  request time, the option that actually served the run, and whether a substitution occurred.
- **Option Evaluation Result**: the recorded strictness measurement for one option against the
  shared benchmark — grounding-violation rate, structural violation rate, malformed-output
  rate, median duration, measured cost per resume — and the evidence behind the default choice.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can discover the generation options, understand what distinguishes them,
  and start a tailoring run on a non-default option in under 30 seconds, without consulting
  documentation.
- **SC-002**: 100% of completed runs display which option produced the resume, and 100% of
  substituted runs are visibly marked as substituted.
- **SC-003**: Choosing the strictest offered option reduces the rule-violation rate on the
  shared benchmark by at least 30% compared with the cheapest offered hosted option — the
  choice measurably changes output quality.
- **SC-004**: Every offered option has a published strictness measurement covering grounding,
  structure, malformed output, duration, and cost per resume, so no option is offered on
  reputation alone.
- **SC-005**: With every hosted provider unavailable, 100% of tailoring runs still complete via
  the self-hosted option.
- **SC-006**: An operator can add, remove, or repoint an offered option in under 5 minutes with
  one configuration edit and one service restart, and users see the change without any client
  update.
- **SC-007**: A user who ignores the selector experiences no change in run duration or output
  quality relative to before this feature.
- **SC-008**: Zero provider credentials or upstream model identifiers are retrievable through
  any application or dashboard surface, verified by inspecting every response the client can
  reach.

## Assumptions

- The existing routing gateway remains the sole owner of provider and model selection; this
  feature adds several named generation options to it rather than introducing a second routing
  mechanism or letting the application name models directly.
- The candidate slate is drawn from the OpenRouter catalogue as read on 2026-08-07, restricted
  to models advertising strict structured-output support, and spans roughly $0.87 to $10 per
  million output tokens — enough range to satisfy FR-011 while keeping the cheapest offered
  option at today's cost. Exact model identifiers are an implementation decision recorded at
  planning time and re-verified against the live catalogue then, since availability and pricing
  move.
- "Cost per resume" is an indicative estimate derived from measured token usage on the
  benchmark, presented as an order-of-magnitude guide, not a billing guarantee.
- Feature 033's strictness work (grounding enforcement, strict output schema, explicit output
  token bounds) lands first or alongside; this feature assumes those rules are the ones every
  option is measured against and does not restate them.
- The self-hosted option is always present and always terminates every chain, per the
  platform's local-first guarantee; it is offered to users as an explicit choice rather than
  only as an invisible last resort.
- User preference storage reuses the existing per-user settings mechanism; this feature does
  not introduce accounts, roles, or per-option permissions.
- Spend controls, budgets, and quotas per option are out of scope; the feature informs about
  cost but does not enforce limits.
- The option list is global to the deployment — every user sees the same options — since this
  is a single-user self-hosted platform.
